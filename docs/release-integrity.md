# Release artifact integrity

English · [Polski](release-integrity.pl.md)

This guide covers the integration ZIP and protocol fuzzer. GitHub-generated source archives are separate artifacts and are not covered by the integration ZIP's checksum or attestation.

## Verify a release archive

Download `ha_linak.zip`, `ha_linak.zip.sha256` and `ha_linak.intoto.jsonl` from the same GitHub Release. Verify the checksum, then verify the Sigstore-backed GitHub build attestation and its release-tag source:

```sh
shasum -a 256 -c ha_linak.zip.sha256
gh attestation verify ha_linak.zip \
  --repo solarssk/ha-linak \
  --signer-workflow solarssk/ha-linak/.github/workflows/release-artifact.yml \
  --source-ref refs/tags/v0.1.0 \
  --bundle ha_linak.intoto.jsonl
```

Replace `v0.1.0` with the release tag you downloaded. Use GitHub CLI 2.49.0 or newer. Install the archive only after both commands succeed. The archive contains `custom_components/ha_linak/`; the checksum detects accidental changes, while the attestation binds the archive digest to the repository's tagged workflow run.

## Build and attach release assets

The maintainer creates the tag and GitHub Release separately. The manual [release artifact workflow](../.github/workflows/release-artifact.yml) builds from the selected ref and validates the package version against `manifest.json` and `CHANGELOG.md`. Its default publication setting is off. A run on a branch builds and attests a validation artifact without release permissions; a run on a tag checks that its version matches the integration.

To publish assets, first create the release for the tag, then dispatch the workflow on that tag with `Upload signed assets to an existing GitHub Release for this tag` enabled. The publishing job verifies the attestation and uploads the ZIP, SHA-256 checksum and attestation bundle to the existing release. It does not create a tag or release, and it does not overwrite existing release assets. Source archives generated by GitHub are not signed by this workflow.

Build the same installation archive locally with:

```sh
python scripts/build_release_artifact.py --output-dir dist
```

For a tagged build, also provide its tag, for example `--tag v0.1.0`. The archive contains only the integration directory, excludes Python bytecode and cache directories, and uses the tagged commit time instead of the current time. Rebuilding the same commit with the same Python and zlib toolchain produces the same ZIP bytes.

## Fuzz the protocol decoders

On Linux x86_64, install the development requirements, then run the bounded Atheris fuzzer:

```sh
python -m pip install -r requirements-dev.txt
python fuzz/fuzz_protocol.py --duration-seconds 30
```

The harness exercises the pure position, capability, offset, stored-position, reminder, research and activation decoders with arbitrary bytes and synthetic framing seeds. It checks accepted result types and numeric invariants; unexpected exceptions fail the run. CI runs the same harness for 30 seconds in the required Tests job. Atheris 3.1.0 currently publishes a Python 3.14 wheel only for Linux x86_64, so the standard macOS development requirements omit it. The fuzzer does not import Home Assistant, scan Bluetooth, connect to a desk or issue movement commands. Atheris detection by Scorecard is not OSS-Fuzz enrollment or a hardware test.
